# 第 9 篇：Agent Runtime 与 Tool Calling——Agent 如何完成一次请求

上一部分我们看到了请求在项目中如何执行：前端可以使用 `await fetch()`，FastAPI 同时存在 `def` 和 `async def`，而数据库、文件解析和模型调用不一定都是异步的。

这一部分继续看工作台中的课程 Agent。重点不是单独介绍某个 Agent 框架，而是沿着一次真实的聊天请求，看清楚下面几个问题：

```text
前端发送的 message 如何进入 Agent？
Agent 和 Runner 分别负责什么？
模型为什么能够调用 Python Tool？
Tool 如何知道当前用户和当前课程？
对话历史和任务等业务数据分别保存在哪里？
```

本篇涉及的真实文件：

```text
web/src/composables/useCourseWorkspace.js
  前端发送课程 Agent 聊天请求

backend/src/course_agent/api/schemas.py
  ChatRequest 请求模型

backend/src/course_agent/api/routers/chat.py
  chat_api、课程归属检查、Agent 请求编排

backend/src/course_agent/agent_runtime.py
  Agent、Runner、SQLiteSession、ContextVar、模型配置

backend/src/course_agent/tools.py
  function_tool、用户和课程作用域、任务与资料操作

backend/src/course_agent/models.py
  ToolResponse、PlanSource 等数据结构
```

## 1. 先看一次聊天请求的整体链路

从当前代码来看，用户在工作台发送一条消息以后，大致会经过下面的过程：

```text
Vue 工作台
  ↓ POST /api/v1/chat
FastAPI 解析 ChatRequest
  ↓
JWT 验证，得到 current_user
  ↓
检查 course_id 是否属于当前用户
  ↓
设置当前请求的 user_id、course_id 和资料来源上下文
  ↓
创建或复用课程 Agent
  ↓
创建 SQLiteSession，读取本次会话历史
  ↓
Runner.run_sync(..., max_turns=6)
  ↓
DeepSeek 模型决定直接回答，或者请求调用 Tool
  ↓
Tool 使用当前用户和课程上下文访问数据服务
  ↓
PostgreSQL、课程资料检索服务或其他确定性代码返回结果
  ↓
模型根据 Tool 结果生成 final_output
  ↓
FastAPI 返回 reply 和 sources
  ↓
前端显示 assistant 消息
```

这条链路中有三个容易混淆的对象：

```text
Agent
  → 描述“这个助手是谁、能做什么”

Runner
  → 驱动“这次请求怎样运行”

SQLiteSession
  → 保存“这个会话之前聊过什么”
```

它们不是同一个东西。Agent 更接近配置，Runner 更接近执行器，Session 更接近对话历史存储。

## 2. 前端如何发送聊天请求

聊天入口位于：

```text
web/src/composables/useCourseWorkspace.js
```

核心函数是 `sendChat`：

~~~javascript
async function sendChat() {
  const message = chatInput.value.trim()
  const course = selectedCourse.value

  if (!message || !course || chatSending.value) {
    return
  }

  activateCourseAgentChat(course.id)
  const messages = chatMessagesByCourse.value[course.id]
  messages.push({
    role: "user",
    content: message,
  })
  chatInput.value = ""
  chatSending.value = true

  try {
    const data = await requestJson(
      "/api/v1/chat",
      {
        method: "POST",
        headers: {
          "Content-Type": "application/json",
        },
        body: JSON.stringify({
          session_id: sessionId,
          course_id: course.id,
          message,
        }),
      },
      "Agent 请求失败",
    )

    messages.push({
      role: "assistant",
      content: data.reply,
      sources: data.sources || [],
    })
  } catch (exception) {
    messages.push({
      role: "assistant",
      content: `请求失败：${exception.message}`,
    })
  } finally {
    chatSending.value = false
  }
}
~~~

前端发送的 JSON 字段是：

```json
{
  "session_id": "前端会话标识",
  "course_id": "当前课程 ID",
  "message": "用户输入的问题"
}
```

这里要区分 JavaScript 变量名和真正的请求字段。代码中的变量叫 `sessionId`，但 `JSON.stringify` 以后发送的字段叫 `session_id`。

请求中没有 `user_id`。前端的用户身份由 `requestJson` 构造的认证请求头携带，后端再从 JWT 中得到当前用户。这样可以避免把“我是谁”交给客户端自己填写。

`sendChat` 中的 `await requestJson(...)` 只表示前端等待 HTTP 响应。它不能说明后端一定使用了 `async def`，也不能说明 Agent 内部的模型调用、Tool 调用或数据库访问都是异步的。

## 3. ChatRequest 如何校验输入

后端请求模型位于：

```text
backend/src/course_agent/api/schemas.py
```

项目先定义了公共请求配置：

~~~python
class RequestSchema(BaseModel):
    model_config = ConfigDict(
        extra="forbid",
        str_strip_whitespace=True,
    )
~~~

聊天请求继承这个基类：

~~~python
class ChatRequest(RequestSchema):
    """Course-scoped Agent conversation request."""

    session_id: str = Field(min_length=1)
    course_id: str = Field(min_length=1)
    message: str = Field(min_length=1)
~~~

这里的限制分别解决了几个问题：

```text
min_length=1
  → 不接受空的 session_id、course_id 和 message

str_strip_whitespace=True
  → 对字符串去掉首尾空白

extra="forbid"
  → 请求中出现未定义字段时拒绝请求
```

这一步只是输入校验，不等于授权校验。例如，`course_id` 非空，只能说明它格式上有值，不能说明它属于当前用户。课程归属还要在 `chat_api` 中单独检查。

## 4. chat_api 如何完成认证和课程隔离

聊天路由位于：

```text
backend/src/course_agent/api/routers/chat.py
```

入口函数是一个普通同步函数：

~~~python
@router.post("/chat")
def chat_api(
    request: ChatRequest,
    current_user: dict = Depends(get_current_user),
) -> dict:
    """Run the Agent constrained to the currently selected course."""
~~~

`current_user: dict = Depends(get_current_user)` 是 FastAPI 的依赖注入。请求进入函数体以前，FastAPI 会先执行 `get_current_user`，从认证信息中验证 JWT。验证通过以后，才会把当前用户传给 `chat_api`。

函数体中首先取出用户 ID 和客户端请求的课程 ID：

~~~python
user_id = int(current_user["id"])
course_id = request.course_id.strip()
~~~

接下来，后端不是直接相信客户端提供的 `course_id`，而是从当前用户拥有的课程中查找：

~~~python
course = next(
    (
        item
        for item in list_courses_data(user_id=user_id)
        if item.id == course_id
    ),
    None,
)

if course is None:
    raise HTTPException(
        status_code=404,
        detail="没有找到当前课程。",
    )
~~~

这里的安全边界可以写成：

```text
客户端提供 course_id
  ↓
JWT 提供 user_id
  ↓
list_courses_data(user_id=user_id)
  ↓
只在当前用户拥有的课程中匹配 course_id
```

如果用户试图把别人的课程 ID 放进请求，课程归属检查就找不到对应课程，Agent 不会被创建，也不会进入后续 Tool 调用。

这里有一个重要区别：

```text
ChatRequest 校验
  → “course_id 有没有值？”

课程归属检查
  → “这个 course_id 是否属于 JWT 对应的用户？”
```

前者是 schema 校验，后者才是访问控制的一部分。

## 5. Agent 配置和 Agent 实例缓存

课程归属检查通过以后，`chat_api` 会调用 `get_runtime_agent`：

~~~python
def get_runtime_agent(course_id: str, course_name: str):
    """Create and reuse an isolated Agent configuration per course."""
    agent = _course_agents.get(course_id)
    if agent is None:
        agent = create_course_agent(
            course_id=course_id,
            course_name=course_name,
        )
        _course_agents[course_id] = agent
    return agent
~~~

它使用进程内字典缓存 Agent：

~~~python
_course_agents: dict[str, object] = {}
~~~

缓存键是 `course_id`。所以从当前代码不能得出“不同用户一定会创建不同 Agent”这个结论。更准确的说法是：

```text
Agent 配置
  → 按 course_id 缓存，可以复用

用户身份
  → 不放在 Agent 配置中，而是来自 JWT 和请求上下文

对话历史
  → 通过包含 user_id、course_id 和 session_id 的 SQLiteSession 隔离
```

也就是说，Agent 本身主要保存课程名称、提示词和 Tool 列表，不应该被当成某个用户的业务数据容器。用户隔离依靠后面的确定性校验和请求上下文完成。

当前缓存还有一个项目边界：它位于单个进程内存中。进程重启以后缓存会消失；如果部署多个 worker，各 worker 也不会共享这份字典。这属于当前实现的运行时限制，不是本篇要修改的问题。

## 6. create_course_agent 做了什么

真正用于 Web 课程聊天的是 `create_course_agent`，位于：

```text
backend/src/course_agent/agent_runtime.py
```

核心结构如下：

~~~python
def create_course_agent(
    *,
    course_id: str,
    course_name: str,
) -> Agent:
    """Create a course-bound Agent with its own conversational identity."""
    configure_model()

    return Agent(
        name=f"{course_name}课程助手",
        model="deepseek-v4-flash",
        instructions=f"""
你是“{course_name}”的专属课程 Agent。

当前唯一可处理的课程 ID：{course_id}。
...
""",
        tools=[
            list_tasks,
            get_task_detail,
            create_task,
            update_task,
            update_task_status,
            delete_task,
            search_course_documents,
            list_deadline_risks,
        ],
    )
~~~

这个 Agent 主要由四部分组成：

```text
name
  → 对话中使用的助手名称

model
  → 本项目配置的 DeepSeek 模型

instructions
  → 课程范围、查询规则、写入规则、删除确认规则等

tools
  → 模型可以请求使用的 Python Tool
```

当前 Web 课程 Agent 可用的 Tool 是：

```text
只读类：
  list_tasks
  get_task_detail
  search_course_documents
  list_deadline_risks

写入类：
  create_task
  update_task
  update_task_status

高影响操作：
  delete_task
```

这里的“只读类、写入类、高影响操作”是对当前 Tool 的分析分类，不是项目中已经存在的独立风险策略引擎。当前代码没有一个统一的 `ToolPolicy` 或手写权限注册表来自动执行这些分类。

另外，`agent_runtime.py` 中还有一个 `create_agent()`。它创建的是可以选择课程范围的通用 Agent，并且包含 `list_courses`。当前 Web 的 `/api/v1/chat` 路由调用的是 `create_course_agent()`，不是 `create_agent()`，所以不能把两个 Agent 的 Tool 列表混在一起。

## 7. configure_model 如何配置 DeepSeek

`create_course_agent` 创建 Agent 前会调用 `configure_model()`：

~~~python
def configure_model() -> None:
    """配置 DeepSeek OpenAI 兼容客户端。"""
    global _model_configured

    if _model_configured:
        return

    load_project_env()
    api_key = os.getenv("DEEPSEEK_API_KEY")

    if not api_key:
        raise RuntimeError(
            "没有找到 DeepSeek API Key。请在项目根目录的 .env 文件中设置："
            "DEEPSEEK_API_KEY=你的DeepSeek_API_Key"
        )

    deepseek_client = AsyncOpenAI(
        api_key=api_key,
        base_url="https://api.deepseek.com",
    )

    set_default_openai_client(
        deepseek_client,
        use_for_tracing=False,
    )
    set_default_openai_api("chat_completions")
    set_tracing_disabled(True)

    _model_configured = True
~~~

这段代码做的是模型客户端配置，而不是运行一次 Agent 请求：

```text
load_project_env()
  → 加载项目环境变量

DEEPSEEK_API_KEY
  → 从环境变量读取 API Key

AsyncOpenAI(..., base_url="https://api.deepseek.com")
  → 创建使用 DeepSeek OpenAI 兼容接口的客户端

set_default_openai_client(...)
  → 让 Agents SDK 使用这个客户端

_model_configured
  → 防止重复配置
```

这里的 `AsyncOpenAI` 只说明客户端支持异步接口，不能据此判断本项目的 `/api/v1/chat` 一定是异步执行。当前聊天路由调用的是 `Runner.run_sync()`，这一点要看实际调用链，而不是只看客户端类名。

## 8. Agent 和 Runner 分别负责什么

`chat_api` 中把 Agent、用户消息和 Session 传给 `run_agent_message`：

~~~python
result = run_agent_message(
    agent=agent,
    user_input=request.message,
    session=session,
)
~~~

`run_agent_message` 的实现是：

~~~python
def run_agent_message(
    agent: Agent,
    user_input: str,
    session: SQLiteSession,
):
    """运行一次 Agent 请求。"""
    return Runner.run_sync(
        agent,
        user_input,
        max_turns=6,
        session=session,
    )
~~~

可以按照下面的方式理解：

```text
Agent
  → 提供模型、instructions 和 tools

Runner
  → 启动一次运行，协调模型、Tool 和最终结果

user_input
  → 本次用户消息

session
  → 让本次运行能够读取和继续已有对话

max_turns=6
  → 限制一次 Agent 运行最多进行 6 轮
```

`max_turns=6` 限制的是一次 Agent 执行过程的轮数，不是用户在接口层面最多能发送 6 次请求。例如，一次用户消息可能触发模型回答，也可能触发若干次“模型请求 Tool—Tool 返回—模型继续判断”的循环；这些循环受到 `max_turns` 限制。

如果超过最大轮数，`chat_api` 会捕获 `MaxTurnsExceeded`；如果模型返回无效的 Tool 调用，会捕获 `ModelBehaviorError`。这两种失败不会被当作成功回复返回。

当前接口使用 `Runner.run_sync()`，所以它会等待 Agent 得到完整结果后再返回。前端目前没有收到 Agent 中间事件，也没有 SSE 流式输出。

## 9. Tool Calling 是怎样发生的

当前 Tool 使用 `@function_tool` 修饰 Python 函数。例如课程资料搜索：

~~~python
@function_tool
def search_course_documents(
    course: str,
    query: str,
) -> str:
    """Search the selected course's parsed materials by query."""
~~~

Agents SDK 会根据函数签名、类型注解和 docstring 生成 Tool 的参数 schema。项目中没有另外维护一份独立的手写 JSON Tool 注册表。

因此模型能看到的不是一段可以随便执行的 Python 源码，而是类似下面的信息：

```text
工具名称：search_course_documents
参数：
  course: str
  query: str
用途：搜索当前课程已经解析的资料
```

一次 Tool Calling 的过程更准确地说是：

```text
用户提出问题
  ↓
Runner 把 Agent 的 instructions 和可用 Tool 描述提供给模型
  ↓
模型返回普通回答，或返回结构化的 Tool 调用请求
  ↓
Agents SDK 在服务端调用对应的 Python 函数
  ↓
Python Tool 调用数据服务、业务逻辑或数据库
  ↓
Tool 返回 JSON 字符串
  ↓
Runner 把 Tool 结果交给模型继续判断
  ↓
模型生成 final_output
```

所以，模型并没有直接执行 Python，也没有直接连接 PostgreSQL。模型只负责理解问题、选择 Tool 和填写参数；真正的 Python 函数、用户隔离和数据库访问仍然由服务端代码控制。

以用户询问“这门课有哪些未完成任务？”为例，当前课程 Agent 可能选择：

```text
list_tasks(course=当前课程 ID, status="todo")
  ↓
list_tasks_data(user_id=当前用户 ID, course=当前课程, status="todo")
  ↓
PostgreSQL 查询任务
  ↓
ToolResponse.success_response(...)
  ↓
模型把结构化任务结果组织成中文回答
```

这里“用模型语言发给用户”是对的，但顺序要说准确：不是 Tool 自己把结果改写成人话，而是 Tool 返回结构化结果后，Runner 再让模型根据这个结果生成 `final_output`。

## 10. Tool 如何获得用户和课程上下文

Tool 的函数参数中通常没有 `user_id`。以 `list_tasks` 的数据调用为例：

~~~python
tasks = list_tasks_data(
    user_id=_current_document_user_id(),
    course=_current_agent_course_id() or course,
    status=status,
)
~~~

`_current_document_user_id()` 使用延迟导入取得当前 Agent 用户：

~~~python
def _current_document_user_id() -> int:
    # Import lazily to avoid the agent_runtime -> tools import cycle.
    from .agent_runtime import get_current_agent_user_id

    return get_current_agent_user_id()
~~~

真正读取用户上下文的函数是：

~~~python
def get_current_agent_user_id() -> int:
    user_id = _agent_user_id.get()
    if user_id is None:
        raise RuntimeError("当前 Agent 请求缺少用户上下文。")
    return user_id
~~~

课程上下文的读取逻辑类似。`_current_agent_course_id()` 在没有课程上下文时会捕获 `RuntimeError` 并返回 `None`，这是为了兼容旧的、可以不绑定课程的命令行 Agent；Web API 在调用课程 Agent 前会设置课程上下文。

需要注意这一句：

~~~python
course=_current_agent_course_id() or course
~~~

在 Web 聊天中，服务端设置的当前课程优先于模型传入的 `course` 参数。也就是说，模型即使错误地填写了另一个课程 ID，课程作用域也不会只由模型参数决定。

## 11. ContextVar 什么时候创建、什么时候设置

`agent_runtime.py` 定义了三个请求上下文：

~~~python
_agent_user_id: ContextVar[int | None] = ContextVar(
    "agent_user_id",
    default=None,
)

_agent_course_id: ContextVar[str | None] = ContextVar(
    "agent_course_id",
    default=None,
)

_agent_document_sources: ContextVar[list[PlanSource] | None] = ContextVar(
    "agent_document_sources",
    default=None,
)
~~~

当 Python 第一次导入 `agent_runtime.py` 时，创建的是三个 `ContextVar` 对象。默认值是 `None`，但不能把这句话理解成“变量对象本身变成了 None”。更准确地说：

```text
_agent_user_id
  → ContextVar 对象

_agent_user_id.get()
  → 当前执行上下文中的值；尚未设置时为 None
```

在 `chat_api` 完成 JWT 验证和课程归属检查以后，才设置这些请求上下文：

~~~python
user_token = set_current_agent_user_id(user_id)
course_token = set_current_agent_course_id(course.id)
source_token = set_current_agent_document_sources()
~~~

例如用户 ID 的设置函数是：

~~~python
def set_current_agent_user_id(user_id: int) -> Token:
    """Scope document tools to the authenticated chat user."""
    return _agent_user_id.set(user_id)
~~~

`set()` 返回一个 `Token`。这个 Token 记录了设置前的上下文状态，后面可以用来恢复：

~~~python
finally:
    reset_current_agent_document_sources(source_token)
    reset_current_agent_course_id(course_token)
    reset_current_agent_user_id(user_token)
~~~

这段 `finally` 很重要。它确保 Agent 请求结束时，无论是正常返回、超过最大轮数，还是发生异常，都不会把本次请求的用户、课程和资料来源留给后续请求。

因此，本项目中 `ContextVar` 的作用不是保存永久业务数据，而是把“当前请求的安全上下文”传递给 Tool：

```text
chat_api 设置 user_id/course_id
  ↓
Agent Runner 执行 Tool
  ↓
Tool 从 ContextVar 读取上下文
  ↓
finally 恢复上下文
```

## 12. Tool 如何把上下文带到数据库和资料服务

### 12.1 任务 Tool

以 `get_task_detail` 为例，它不会直接拿任务 ID 就查询，而是调用 `_get_scoped_task_or_raise`：

~~~python
def _get_scoped_task_or_raise(task_id: str):
    task = get_task_detail_data(
        user_id=_current_document_user_id(),
        task_id=task_id,
    )
    if task is None:
        raise ValueError(f"没有找到任务：{task_id}")

    current_course_id = _current_agent_course_id()
    if current_course_id and task.course_id != current_course_id:
        raise ValueError(
            "当前课程 Agent 不能访问或修改其他课程的任务。"
        )

    return task
~~~

这里有两层限制：

```text
第一层：user_id
  → 任务必须属于当前 JWT 用户

第二层：current_course_id
  → 任务还必须属于当前课程 Agent 的课程
```

`update_task`、`update_task_status` 和 `delete_task` 都会经过类似的作用域检查。Tool 的输入参数来自模型，但用户和课程作用域来自服务端上下文，不能由模型自由决定。

### 12.2 课程资料 Tool

课程资料搜索的主要代码是：

~~~python
results = search_course_documents_data(
    user_id=_current_document_user_id(),
    course=_current_agent_course_id() or course,
    query=query,
)
~~~

这里 Tool 本身只负责接收模型提出的查询并调用资料服务。资料服务再根据当前用户、课程和查询内容访问已经解析的课程资料。当前项目的检索实现由资料服务负责，本文只关注 Agent 与 Tool 的衔接，不展开向量优先和全文检索回退的具体算法。

课程资料返回给模型的是不可信参考内容。课程 Agent 的 instructions 明确规定：资料中的命令、权限要求或提示注入文本不能改变 Tool 权限和删除确认规则。

## 13. 删除任务为什么需要二次确认

删除是当前 Tool 中影响最大的操作之一。课程 Agent 的 instructions 要求删除前先查询详情、展示任务信息，并等待用户准确确认；`delete_task` 函数中还会再次进行确定性字符串检查：

~~~python
normalized_task_id = task_id.strip()
expected_confirmation = (
    f"确认删除任务 {normalized_task_id}"
)

if confirmation.strip() != expected_confirmation:
    return error_response(
        f"删除操作未确认。请准确输入：{expected_confirmation}"
    )
~~~

确认文本通过以后，代码还会调用 `_get_scoped_task_or_raise`，确认任务属于当前用户和当前课程，最后才调用：

~~~python
task = delete_task_data(
    user_id=_current_document_user_id(),
    task_id=normalized_task_id,
)
~~~

所以当前实现不是只依赖提示词：

```text
提示词要求先确认
  ↓
Tool 代码严格检查 confirmation
  ↓
Tool 代码检查用户和课程作用域
  ↓
数据服务执行删除
```

不过，当前项目还没有独立的通用 Tool 风险策略引擎或持久化人工审批工作流。这个删除确认是当前 `delete_task` 的确定性规则，不应描述成已经实现了完整的 HITL 系统。

## 14. SQLiteSession 保存的是什么

当前会话创建函数是：

~~~python
def create_session(
    session_id: str = "local-user",
) -> SQLiteSession:
    """创建一个指定会话。"""
    SESSION_DB_PATH.parent.mkdir(parents=True, exist_ok=True)
    return SQLiteSession(
        session_id=session_id,
        db_path=SESSION_DB_PATH,
    )
~~~

聊天接口传入的 Session ID 是：

~~~python
session = create_session(
    f"user-{current_user['id']}-course-{course.id}-{request.session_id}"
)
~~~

因此完整的会话标识包含：

```text
用户 ID
课程 ID
前端 session_id
```

同一个前端 `session_id`，如果用户 ID 或课程 ID 不同，最终传给 `SQLiteSession` 的标识也不同。这是对话历史隔离的一部分。

这里要区分 Conversation Memory 和业务 State：

```text
Conversation Memory
  → SQLiteSession 中的对话历史
  → 供下一次 Runner 运行继续理解上下文

业务 State
  → PostgreSQL 中的课程、任务、资料、学习计划等
  → 通过 Tool 和数据服务查询或修改
```

例如，模型“记得”用户上一轮说过什么，属于会话历史；任务是否已经完成，不能只看会话历史，而要通过 `update_task_status` 写入业务数据，再由任务查询读取。

从当前仓库能够确认的是：项目创建了 Agents SDK 的 `SQLiteSession`，指定了 `session_id` 和 `db_path`，并在聊天运行中传给 Runner。第三方 `SQLiteSession` 内部使用什么表结构、是否压缩历史、何时清理旧记录，当前不能仅从本项目代码确认，不能在学习笔记里把这些细节写成项目已经实现的逻辑。

## 15. Tool 结果如何变成前端看到的回复

Tool 通常返回 JSON 字符串，统一结构来自 `ToolResponse`：

~~~python
class ToolResponse(BaseModel):
    success: bool
    data: Any = None
    error: str | None = None
~~~

模型得到 Tool 结果以后，Runner 最终产生 `result.final_output`。`chat_api` 再把它包装成接口响应：

~~~python
return ToolResponse(
    success=True,
    data={
        "session_id": request.session_id,
        "course_id": course.id,
        "reply": result.final_output,
        "sources": [
            source.model_dump(mode="json")
            for source in get_current_agent_document_sources()
        ],
    },
).model_dump(mode="json")
~~~

资料搜索 Tool 还会把检索结果转换成 `PlanSource`，记录文件、分块、页码和最多 1400 个字符的摘要：

~~~python
PlanSource(
    chunk_id=result.chunk_id,
    chunk_index=result.chunk_index,
    file_id=result.file_id,
    file_name=result.file_name,
    page=result.page,
    excerpt=result.content[:1_400],
)
~~~

这些来源会暂存在本次请求的 `_agent_document_sources` 中，最终由 `chat_api` 放进响应的 `sources` 字段。前端收到响应后使用：

~~~javascript
messages.push({
  role: "assistant",
  content: data.reply,
  sources: data.sources || [],
})
~~~

所以一次资料问答中有两条结果路径：

```text
Tool 的 JSON 结果
  → 返回给 Runner
  → 模型组织成 result.final_output
  → 前端显示 data.reply

检索来源 PlanSource
  → 请求上下文收集
  → chat_api 返回 sources
  → 前端显示引用信息
```

## 16. 把一次请求完整串起来

现在把前面的内容合在一起，可以得到当前 `/api/v1/chat` 的完整执行过程：

```text
1. 用户在 Vue 工作台输入问题
   sendChat() 调用 requestJson()

2. 前端发送 session_id、course_id、message
   认证请求头中携带 JWT

3. FastAPI 校验 ChatRequest
   非空、去除首尾空白、拒绝额外字段

4. Depends(get_current_user) 验证 JWT
   得到 current_user 和 user_id

5. list_courses_data(user_id=user_id)
   检查客户端提供的 course_id 是否属于当前用户

6. set_current_agent_user_id()
   set_current_agent_course_id()
   set_current_agent_document_sources()

7. get_runtime_agent()
   按 course_id 创建或复用课程 Agent

8. create_session()
   使用 user_id、course_id 和前端 session_id 构造会话标识

9. Runner.run_sync(agent, message, max_turns=6, session=session)
   读取对话历史并启动本次 Agent 运行

10. DeepSeek 模型判断下一步
    直接回答，或请求调用当前 Agent 可用的 Tool

11. Tool 从 ContextVar 读取 user_id/course_id
    调用任务服务、资料服务和 PostgreSQL 等确定性代码

12. Tool 返回 JSON 结果
    Runner 将结果再次交给模型

13. 模型生成 final_output
    chat_api 组装 reply、course_id 和 sources

14. finally 重置 ContextVar
    防止本次请求的上下文泄漏到后续请求

15. 前端读取 data.reply 和 data.sources
    显示 Agent 回复及资料来源
```

这里可以看到，真正的安全边界并不只有 Agent instructions：

```text
JWT 验证
  +
课程归属检查
  +
ContextVar 中的服务端用户/课程上下文
  +
数据服务中的 user_id 过滤
  +
Tool 自己的确定性参数和确认检查
```

模型负责理解和规划，但不能替代这些确定性检查。

```text
  → create_course_agent()

  → 进程内按 course_id 复用

模型配置

  → Runner.run_sync(max_turns=6)

  → delete_task 的精确 confirmation 检查

资料来源返回
  → PlanSource + chat response.sources

错误处理
  → MaxTurnsExceeded、ModelBehaviorError 和通用异常分支
```

### 17.2 路线图中的后续方向

路线图把下面这些列为后续工程方向，而不是当前聊天已经具备的能力：

```text
确定性的通用 Tool 风险策略
通用的人在回路中审批
持久化 Agent state、checkpoint 和 resume
SSE / Agent 事件流
请求取消
Agent 追踪与评估
```

它们分别解决权限决策、人工确认、长流程恢复、过程展示和质量衡量问题。当前学习笔记只记录它们的计划状态，不把它们写成现有实现。

### 17.3 当前尚未实现或存在边界

从当前代码和架构文档来看，还需要明确以下边界：

- 当前 `/api/v1/chat` 使用 `Runner.run_sync()`，返回完整结果，没有流式响应。
- `await run_in_threadpool(...)` 或同步 Endpoint 的线程池执行，不等于脱离 HTTP 请求的后台任务。
- Agent 缓存和内存中的请求辅助状态不能跨多个 worker 共享。
- `SQLiteSession` 是对话历史，不是任务、课程或学习计划的业务状态机。
- 当前没有独立的通用 Tool 权限引擎和持久化审批工作流。
- 当前不能仅从项目代码确认 `SQLiteSession` 内部的表结构、压缩和清理策略。

这一篇的核心不是“模型会调用函数”这么简单，而是要看清楚：模型只是请求 Tool，真正决定能不能访问数据、访问哪门课程、能不能删除任务的，仍然是后端的认证、作用域和确定性代码。
